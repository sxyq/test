## 1. 本次验证做了什么

本次不是尝试在 Apple GPU 上完整复刻 AI Studio 的 CUDA 推理，而是按“轻量但尽量全面”的原则，做了 4 类本地验证：

1. `seq_encoder` 合成输入微基准：
   - CPU
   - MPS
2. `RepEncoder` 可运行性验证：
   - CPU 正常
   - MPS 是否可跑
3. `split-device` 验证：
   - `RepEncoder` 走 CPU
   - `seq_encoder + linear` 走 MPS
4. 官方数据真实格式小样本验证：
   - 从 `research_datasets/2026_cti_data_meta` 抽真实 `history/test/label`
   - 构造轻量 batch，验证真实格式下的 split-device 表现

## 2. 本地环境结论

- 机器：Apple Silicon，`macOS 26.5.1`
- Python：`3.9.6`
- PyTorch：`2.4.1`
- `torch.backends.mps.is_available() == True`
- `torch.cuda.is_available() == False`

结论：

- **MPS 可以承接 Transformer 主干验证**
- **MPS 不能直接承接当前完整 GRAB 前向**

核心阻塞点：

- `RepEncoder.forward_segment_reduce()` 使用了 `torch.segment_reduce`
- 该算子在 MPS 上直接报 `NotImplementedError`

因此，本机可行路径是：

1. `seq_encoder` 单独验证
2. `RepEncoder(cpu) -> seq_encoder(mps)` 的 split-device 验证

## 4. 关键问题清单

### 4.1 MPS 阻塞

`RepEncoder` 在 MPS 上失败：

- 错误类型：`NotImplementedError`
- 算子：`aten::segment_reduce`

这意味着：

- 当前 submission 不能原样跑完整 MPS 前向
- 必须改成 split-device 或局部主干验证

### 4.2 默认版本稳定性

`V178-FFN-SVD32-sxyq` 在 CPU 合成微基准中默认报错：

- 错误：`expected m1 and m2 to have the same dtype, but got: float != c10::Half`

这不是“稍慢”，而是默认形态就不稳。

### 4.3 纯工程版不占优

在当前本机上：

- `V179-PURE-ENGINEERING-sxyq`
- `V180-MAXAUTOTUNE-sxyq`

整体都没有跑赢 `V176/V177` 这一组结构压缩路线。

结论很明确：

- 本地 Apple 机器上，**结构减算**比“继续堆 compile 命名版本”更有价值。

## 5. 合成微基准结论

默认合成 `seq_encoder` CPU 微基准里，稳定组大致排序是：

1. `V177-FFN-NOBIAS-sxyq`
2. `V176-FFN-PRUNE-sxyq`
3. `V169-HYBRID-SVD-sxyq`
4. `V175-HEAD-PRUNE-FIX-sxyq`
5. `V181-FFN-PRUNE50-sxyq`
6. `V180-MAXAUTOTUNE-sxyq`
7. `V179-PURE-ENGINEERING-sxyq`

但这组结果只能说明：

- 默认合成张量下，`V176/V177` 是更稳的 CPU 主干候选
- 不能单独拿它决定最终本地推荐版本

原因：

- 合成输入没有真实 `user_offsets` 分布
- 没有真实 CTR 样本的 slot 稀疏结构
- 没有把 `RepEncoder(cpu) -> seq_encoder(mps)` 链路包含进去

## 11. 新增：真实权重 holdout 搜索

在补齐 `weights/ckpt.pt` 之后，又新增了一轮更接近“真实模型路径”的本地搜索：

- 抽样方式：
  - 每个文件取前 `5000` 行
  - 共 `10000` 条样本
  - `1683` 个用户
  - 每个有至少 2 条样本的用户，取最后 1 条做本地 holdout
  - holdout 共 `1293` 条，其中正样本 `49` 条

### 11.1 搜索目标

这轮不再问“175-180 谁更好”，而是直接搜索一个**本地证据上更强的新组合**。搜索空间重点放在：

1. `FFN prune ratio`
2. `SVD rank`
3. `bias` 校准是否需要调整

其中：

- 结构配置通过真实权重重新加载后实际跑前向比较
- `bias` 不重新加载模型，而是对 logits 做后处理扫描

### 11.2 搜索结论

#### 第一层：prune ratio 扫描（rank 固定 128）

| 配置 | CPU holdout latency(s) | AUC | 结论 |
|---|---:|---:|---|
| `prune25_rank128` | **2.7749** | 0.74403 | 当前结构基线 |
| `prune40_rank128` | 3.6059 | **0.74528** | AUC略高，但明显更慢 |
| `prune45_rank128` | 4.1857 | 0.74477 | 更慢 |
| `prune50_rank128` | 4.5054 | 0.74482 | 更慢 |

这一轮说明一个很重要的事实：

- **在真实权重 CPU holdout 路径里，50% 剪枝并没有成为更优主线**
- 之前 `V181` 在轻量 split-device 代理里更强，说明它对“主干算量”有优势
- 但在真实模型完整路径里，更激进的剪枝没有转化为更好的整体 proxy latency

#### 第二层：在 `prune25` 上扫 rank

| 配置 | CPU holdout latency(s) | AUC | 结论 |
|---|---:|---:|---|
| `prune25_rank128` | 4.6156 | 0.74403 | 对照 |
| `prune25_rank96` | 7.6278 | 0.74455 | 明显更慢 |
| `prune25_rank64` | **4.3218** | **0.74508** | 当前最优 |

这一轮给出的最强局部结论是：

## `prune25 + rank64` 是当前本地真实权重搜索里最好的结构组合

### 11.3 对 bias 的解释

这轮 holdout 上，若强行把 `PCOC` 调到 `1.0`，需要一个**很大的正 bias**（约 `+0.68 ~ +0.74`）。

这个值**不能直接拿去线上默认使用**，原因很明确：

1. 这只是本地 history-holdout 分布，不是官方 test 分布
2. 历史线上记录表明，`V169/V171` 这类小 bias 校准已经比较稳定
3. 本地 holdout 的点击率很低，校准值会非常敏感

所以这轮搜索里：

- **结构结论可信**
- **大幅 bias 数值本身不应直接烘焙进 submission 默认值**

- 当前最均衡的**新版本**
- 仍然快于 `175~180`
- 同时没有像 `V182` 一样在本地 MPS 代理上明显掉队

#### `V176/V177`

- 仍然是本地 Apple MPS 代理上的强基线
- 尤其适合做 split-device 和 real-sample 对照

## 19. 现在最准确的排序

如果只问：

> 有没有一个**新版本**已经本地证据上强于 `175~180` 组？

答案是：

- `V182`：CPU / 结构主线最强
- `V183`：当前最均衡的新版本

如果问：

> 哪个版本最适合当“本地下一提交主线”？

当前我更倾向于：

## `V183-FFN25-SVD64-NOMPS-SVD-sxyq`

1. 它保留了新版本对 `175~180` 的 CPU 优势
2. 它比 `V182` 更接近本地 MPS / split-device / real-sample 的老主线表现

但如果问：

> 哪个版本最能代表“结构极限”？

- `V182`
