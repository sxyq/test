## 1. 这次本地实验的目标

目标不是复刻线上 V100 绝对 latency，而是回答 3 个更关键的问题：

1. 本地哪些版本在当前机器上仍然体现出更强的结构效率；
2. 当前 `submission` 里哪些路线只是线上 CUDA 友好，哪些在本地也有稳定优势；
3. 下一步应该沿哪条版本线继续叠加，而不是盲目回到旧路线。

---

## 2. 本地环境与硬约束

### 2.1 可用加速能力

- `torch.backends.mps.is_available() == True`
- `scaled_dot_product_attention`、Transformer 主干可在 MPS 上运行
- 但 `RepEncoder` 中使用的 `torch.segment_reduce` 在本机 MPS 上仍然 `NotImplemented`

### 2.2 直接影响

- 当前整条 submission 推理链路**不能原样在 MPS 上完整跑通**
- 可做的本地 GPU 验证方式只有两类：
  - `seq_encoder` 主干基准
  - `split-device`：`rep_encoder` 留 CPU，`seq_encoder + head` 放 MPS

这意味着：

- 本地 Apple 机器适合做**结构效率筛选**
- 不适合拿来替代线上 CUDA 最终胜负判断

## 3. 全量本地数据链路的真实结论

### 3.1 全量数据规模

- `research_datasets/2026_cti_data_meta/dataset/test.csv`：`7774` 行
- `label_data.txt`：`7774` 行
- `history/*.csv`：`15` 个 shard
- 整体数据目录体积：约 `14G`

### 3.2 直接跑全量 submission 的结果

做过两次真实尝试：

1. 直接跑 `submission/V184-STACKED-RECALIB-sxyq/infer.py --device cpu --allow-cpu`
2. 通过 `research/build_cached_batches.py` 预构建 `cached_batches`

结论一致：

- 主要瓶颈不在最后几层推理，而在 `load_sample_files -> CTRUserDataset` 的历史序列展开
- 这条 Python 数据链路在本机上做“多版本全量横比”成本过高，不适合作为当前迭代主验证方式

这不是版本性能结论，而是**本地实验方法论结论**：

> 当前本机上，真正值得反复跑的是“共享样本 + 结构基准 + split-device”，不是每个版本都重复吃一次 14G 全量历史展开。

## 4. 真实小样本构造结果

为了让本地验证尽量贴近真实数据，我从正式数据中构造了两档样本。

### 4.1 `real_sample_1024`

- 取前 `1024` 条 `test.csv`
- 涉及 `974` 个用户
- 过滤 15 个 history shard 后，保留 `295,289` 条历史记录
- 样本目录大小约 `472M`

共享加载实验结果：

- `data_load_seconds = 48.56s`
- `batch_build_seconds = 38.36s`
- `total_samples = 296,284`
- `num_batches = 20`

结论：

- 虽然 test 只有 `1024` 条，但按用户全序列展开后仍然非常大
- 对 CPU 本地端到端横比仍然偏重

### 4.2 `real_sample_128`

- 取前 `128` 条 `test.csv`
- 涉及 `127` 个用户
- 过滤后保留 `32,477` 条历史记录

共享加载实验结果：

- `data_load_seconds = 5.35s`
- `batch_build_seconds = 4.01s`
- `total_samples = 32,605`
- `num_batches = 3`

结论：

- 这档样本适合作为后续本地端到端 smoke / 回归样本
- 但即便如此，端到端 CPU 比纯主干基准仍然重很多

## 5. 轻量结构基准总表

以下结果来自本地真实执行的 `research/local_lightweight_validation.py` 与补充 benchmark。

### 5.1 CPU 主干基准（早期矩阵）

单位：秒，值越小越好；为 `256/512/1024 token` 多档平均表现

| 版本 | 平均时间 |
|---|---:|
| `V182-FFN25-SVD64FP32-sxyq` | **0.07435** |
| `V181-FFN-PRUNE50-sxyq` | 0.08734 |
| `V177-FFN-NOBIAS-sxyq` | 0.08844 |
| `V176-FFN-PRUNE-sxyq` | 0.09112 |
| `V175-HEAD-PRUNE-FIX-sxyq` | 0.10405 |
| `V169-HYBRID-SVD-sxyq` | 0.11580 |
| `V179-PURE-ENGINEERING-sxyq` | 0.14007 |
| `V180-MAXAUTOTUNE-sxyq` | 0.14166 |

结论：

- 本地 CPU 上最强的是 `V182` 线，不是 `V179/V180` 的纯工程 compile 线
- `175~180` 内部最强是 `V177`
- 结构压缩线显著强于纯 runtime 线

### 5.2 新增版本 CPU 主干基准（逐 token）

| 版本 | 256 | 512 | 1024 |
|---|---:|---:|---:|
| `V177-FFN-NOBIAS-sxyq` | 0.02576 | 0.04816 | 0.08612 |
| `V182-FFN25-SVD64FP32-sxyq` | **0.01979** | **0.03673** | **0.07137** |
| `V184-STACKED-RECALIB-sxyq` | 0.02045 | 0.04035 | 0.07553 |
| `V185-V177-STACKED-SUBMIT-sxyq` | 0.02083 | 0.03994 | 0.07567 |
| `V186-ASYNC-PREFETCH-sxyq` | 0.02181 | 0.04239 | 0.07797 |

结论：

- 本地 CPU 主干速度排序非常稳定：`V182 > V184 ≈ V185 > V186 > V177`
- `V185` 在线上整体分最高，但**本地纯主干并没有快过 `V182`**
- `V186` 的异步 prefetch 属于 CUDA/H2D 思路，在本地 CPU 主干基准中没有收益，反而更慢

## 6. MPS 与 split-device 结果

### 6.1 MPS 主干基准

| 版本 | 256 | 512 |
|---|---:|---:|
| `V177-FFN-NOBIAS-sxyq` | 0.01933 | **0.02817** |
| `V182-FFN25-SVD64FP32-sxyq` | 0.02133 | 0.03114 |
| `V184-STACKED-RECALIB-sxyq` | 0.01892 | 0.03349 |
| `V185-V177-STACKED-SUBMIT-sxyq` | **0.01779** | 0.02886 |
| `V186-ASYNC-PREFETCH-sxyq` | 0.02095 | 0.02966 |

备注：

- `V182/V184/V185/V186` 在 MPS 准备阶段都会触发 `aten::linalg_svd` fallback 到 CPU 的告警
- 这会抬高 MPS 侧准备成本

结论：

- 如果只看 `512 token`，`V177` 略优于 `V185`
- 如果看 `256 token`，`V185` 最快
- 说明 `V185` 更像“小中序列友好”的线上综合版，不是本地 MPS 绝对统治版

### 6.2 split-device（`rep_encoder@CPU + seq/head@MPS`）

| 版本 | CPU rep | seq+head | total |
|---|---:|---:|---:|
| `V177-FFN-NOBIAS-sxyq` | 0.00838 | 0.00954 | **0.01792** |
| `V182-FFN25-SVD64FP32-sxyq` | 0.00933 | 0.01225 | 0.02159 |
| `V184-STACKED-RECALIB-sxyq` | 0.00914 | 0.01435 | 0.02348 |
| `V185-V177-STACKED-SUBMIT-sxyq` | 0.00915 | 0.01863 | 0.02778 |
| `V186-ASYNC-PREFETCH-sxyq` | 0.01044 | 0.02093 | 0.03137 |

结论：

- 在“最接近本机可落地的 Apple 路线”里，`V177` 反而是最平衡的
- `V185/V186` 的优势明显更依赖线上 CUDA runtime，而不是本地 Apple 路线

## 7. 有针对性的局部变体结论

来自早期 targeted variants：

- `V182-default` 是本地 CPU targeted 组合最优
- `V182-rank128` 比默认 `rank64` 更慢
- `V176-nosvd` 明显更慢，说明 SVD 在当前路线中不是装饰，而是有效降算
- `V181/176` 去掉 SVD 后也没有出现“更稳更快”的收益

结论：

1. `rank64` 比 `rank128` 更适合当前本地主线；
2. `prune + SVD` 的组合不是问题，反而是目前本地最强结构路线之一；
3. 下一步没必要回退到“先去掉 SVD 再说”。

## 8. 本地实验能支持的明确判断

### 8.1 哪条线本地最强

如果只看**本地结构效率**：

- **最强外部版本**：`V182-FFN25-SVD64FP32-sxyq`
- **175~180 内最强版本**：`V177-FFN-NOBIAS-sxyq`

也就是说：

> 本地已经存在一个明确强于 `175~180` 任意单版的结构候选，就是 `V182` 线。

### 8.2 为什么线上最佳不等于本地最佳

当前线上最强合规结果已经转到 `V185` 线，但本地测试说明：

- `V185` 赢在**校准修复 + 线上 runtime 叠加**
- 不代表它在 CPU/MPS 主干层面一定最强
- `V186` 更明显，它是 H2D/stream overlap 思路，本地无 CUDA 时收益基本看不出来

所以：

- 如果目标是“继续冲线上总分”，要沿 `V185` 往前推
- 如果目标是“在本地先找到更强结构底座”，应继续沿 `V182` 线推

## 9. 下一步构建建议

### 9.1 主线不要再回到纯工程优化

本地结果已经很明确：

- `V179/V180` 纯 compile/runtime 线不如 `V177/V182`
- 下一步主线不该回到“再堆 compile 参数”

### 9.2 建议拆成两条并行线

#### A. 结构主线：以 `V182` 为底

理由：

- 本地 CPU 主干最快
- `rank64 + prune25 + FP32-SVD` 已被反复证明有效
- 问题主要是**校准**，不是结构无效

建议继续叠加：

1. `V182` 结构底座固定；
2. 继续做 bias / 校准扫描；
3. 控制只叠加不会改变排序的零成本修正；
4. 再把 `V185` 中已经验证过的合规 runtime 叠上去。

这条线更像：

> `V182-structure` + `V184/V185 calibration/runtime lessons`

#### B. 线上提交主线：以 `V185` 为底

理由：

- 当前线上总分最强
- 已经证明“校准修回后，结构压缩收益能稳定兑现”

建议继续叠加：

1. 只做合规 runtime 微叠加；
2. 优先看 batch 准备、H2D、prefetch、缓存；
3. 不轻易改动结构主体，避免重新打乱 PCOC。

### 9.3 对 `V186` 的判断

`V186` 不应被当成新的结构主线，只能当：

- `V185` 上的 CUDA runtime 附加实验

本地证据不支持它成为新底座，因为：

- CPU 主干更慢
- MPS / split-device 也更慢

---

## 10. 最值得立刻做的事

按优先级排序：

1. 以 `V182` 为底，新建一个“结构最强 + 校准修复 + 只叠加低风险 runtime”的版本；
2. 以 `real_sample_128` 固化本地端到端 smoke 基线，后续每次只跑 2~3 个候选；
3. 保留 `V185` 作为线上当前主线，不再回退到 `V177` 的无 bias 诊断状态；
4. `V186` 只在需要验证 CUDA H2D 重叠时继续保留，不作为本地主线判断依据。

---

## 11. 最终结论

这次本地实验最重要的结论只有三句：

1. **本地结构最强的不是 `V179/V180` 工程线，而是 `V182` 这条 `prune25 + rank64 + FP32-SVD` 线；**
2. **线上总分最强的 `V185` 依赖的是“结构收益 + 校准修复 + CUDA runtime 叠加”，不能简单等同于本地主干最强；**
3. **下一步正确做法不是回退旧路线，而是把 `V182` 当结构底座，把 `V185` 当线上经验库，做一次新的合并版。**
