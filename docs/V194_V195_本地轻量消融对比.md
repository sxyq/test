# V194 与 V195 本地轻量消融对比

> 数据来源：`12_workspace/real_sample_128`
>
> 原始结果文件：[`12_workspace/v194_v195_local_ablation_results.json`](/Users/sunyiyang/Desktop/Project/Baidu%20%20GRAB/12_workspace/v194_v195_local_ablation_results.json)
>
> 对比对象：
> - `V194-TRT-MOE-STACKED-sxyq`
> - `V195-TRT-MOE-HIGHRISK-sxyq`
> - `V195` 去掉 `balance / bias / prune` 的局部对照

## 1. 线上现象先定性

你给出的线上结果里，`V194` 高于 `V195`：

- `V194`: `70.95097 / PCOC=1.05895 / latency=34.66039 / AUC=0.75261`
- `V195`: `70.48002 / PCOC=0.86655 / latency=35.01999 / AUC=0.75271`

这说明：

1. `AUC` 几乎没坏；
2. `PCOC` 从 `1.05895` 被明显拉低到 `0.86655`；
3. `latency` 也略回退了 `+0.35960s`。

所以 `V195` 的问题不是单一的：

- **掉分主因优先怀疑 `bias`**
- **延迟回退再怀疑 batch 路径或 plugin-side prune**

## 2. 本地轻量验证做了什么

本次本地验证只做你这台 Apple 机器上能真实复现的部分：

1. `CSV -> Dataset -> DataLoader -> group_user_batches_by_token_cap` 的 batch 构造链路；
2. `balanced batching` 对 batch token 分布的影响；
3. cached batch 的读写成本；
4. 用真实 batch shape 驱动 `TransformerEncoder` 的轻量 seq proxy；
5. `bias` 与 `prune` 的“本地可见性”判断。

没有在本地复现的部分：

1. TRT plugin 真正的 CUDA kernel；
2. `prepare_trt_moe()` 内部 plugin-side prune 的真实在线收益；
3. 真实线上 wall-clock 计时口径。

## 3. 关键本地结果

### 3.1 batch 构造链路

`V194`：

- `load_csv_seconds`: `1.7483s`
- `dataset_build_seconds`: `0.9318s`
- `collate_seconds`: `0.5706s`
- `group_seconds`: `0.0480s`

`V195 default`：

- `load_csv_seconds`: `2.0637s`
- `dataset_build_seconds`: `1.1990s`
- `collate_seconds`: `0.6936s`
- `group_seconds`: `0.0442s`

结论：

- `V195` 的重建 batch 路径本地确实更重；
- 但这个成本是否算进线上 latency，要看平台计时边界；
- 如果平台按整段 wall-clock 算，`force rebuild` 是显著风险项；
- 如果平台只记 `start inference` 后的 forward 时间，这部分不是主因。

### 3.2 cached batch 与 rebuild 的差距

本地把最终 batch 序列序列化后再加载，`cached load` 只要约 `0.008s ~ 0.012s`，而从 CSV 重建全链路是 `3s+`。

结论：

- `cached batch` 和 `force rebuild` 的前处理成本差距非常大；
- 这条线在“整脚本 wall-clock 口径”下风险很高；
- 但它解释不了你线上只有 `0.36s` 的小幅回退，说明平台大概率不是把全部 CSV 构造时间原样算进去，或者外部真实数据路径不同于 `real_sample_128`。

### 3.3 balanced batching 的局部作用

`V194` pre-group:

- `batch_count=3`
- `token_min=4305`
- `token_max=15863`

`V195 default` pre-group:

- `batch_count=3`
- `token_min=4288`
- `token_max=15282`

`V195 no_balance` pre-group:

- 与 `V194` 完全一致

说明 `balanced batching` 在 pre-group 阶段确实改变了 batch token 分布，而且把最大 batch 稍微拉平了。

但在当前 `real_sample_128` 上，默认 `token_cap=300000`，三批最后都会被合并成 **一个**大 batch：

- `V194` post-group: `batch_count=1`
- `V195 default` post-group: `batch_count=1`
- `V195 no_balance` post-group: `batch_count=1`

结论：

- 在这个本地样本口径里，`balanced batching` 并没有改变最终进入 seq path 的 batch 数和总 token；
- 它更像只改变了前一层分组形状，而被后续 token-cap regroup 吃掉了；
- 所以它不是当前本地样本里最强的问题嫌疑。

### 3.4 seq proxy 结论

本地 seq proxy 结果有波动，但没有支持“balanced batching 明显变坏”的证据。

反而从对照关系看：

- `V195 default` 比 `V195 no_balance` 更快

所以至少在这套 `real_sample_128 + token_cap=300000` 的轻量代理里：

- `balanced batching` 不是导致 `V195` 比 `V194` 更慢的首要嫌疑。

### 3.5 bias 与 prune 的可见性

`BAIDU_LOGIT_BIAS`：

- 只改输出校准；
- 不应带来真实 latency 收益；
- 但会直接影响 `PCOC`。

`BAIDU_PRUNE_FFN`：

- 在 `V195` 里是写在 `prepare_trt_moe()` 里的；
- 只有 CUDA/TRT plugin 路径真正启用时才生效；
- Apple 本地轻量验证无法直接复现它的真实在线影响。

结论：

- 本地能直接锁定 `bias` 是 score regression 的头号嫌疑；
- 本地不能直接证伪/证实 plugin-side prune 的在线 latency 贡献；
- 如果 `balance` 不是主因，那剩余最该怀疑的在线运行时模块就是 **plugin-side prune**。

## 4. 当前最可信的判断

按优先级排序：

1. **`logit_bias` 是 `V195` 掉分主因**
   - 证据最强；
   - 线上 `AUC` 基本不变，`PCOC` 明显被压低；
   - 这和 `bias` 过负完全一致。

2. **`plugin-side FFN prune` 是 `V195` 延迟回退的首要技术嫌疑**
   - 本地无法直接复现；
   - 但 `balance` 没显示出明显负面；
   - 剩下真正会改 CUDA/TRT kernel 运行形状和效率的，就是它。

3. **`force rebuild batches` 是口径风险项，不一定是这次线上 0.36s 回退的主因**
   - 它在本地前处理里很重；
   - 但与线上只有 `+0.35960s` 的回退量级并不匹配；
   - 更像“如果平台按整脚本计时就危险”，而不是“这次唯一根因”。

4. **`balanced batching` 目前不是头号嫌疑**
   - 在这个本地样本下，它没有把最终 grouped batch 变坏；
   - 甚至局部代理里比 `no_balance` 更快。

## 5. 下一步建议

最值得继续做的是两个在线候选，而不是继续盲叠：

1. `V196-TRT-MOE-DEBIAS-sxyq`
   - 基于 `V195`
   - 只去掉默认 `BAIDU_LOGIT_BIAS=-0.207347...`
   - 其他保持不动
   - 目标：验证 `PCOC` 是否回到 `~1.0` 附近

2. `V197-TRT-MOE-NOPRUNE-sxyq`
   - 基于 `V195`
   - 只关闭 plugin-side `BAIDU_PRUNE_FFN`
   - 保留 batch 路径和其他壳层
   - 目标：验证在线 latency 是否回升到 `V194` 水平

如果只允许先做一个，我会先做 `V196`，因为 `bias` 的问题证据最硬。
