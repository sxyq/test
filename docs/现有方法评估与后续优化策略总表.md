## 1. 这份文档要解决什么问题

当前本地 `submission/` 已经不是“几个候选版本”，而是一个方法库。问题不在于“版本够不够多”，而在于：

1. 哪些方法已经被验证有效，可以继续承接；
2. 哪些方法已经被验证无效，后续不该继续投入；
3. 哪些目录只是本地候选，还没有被正确验证；
4. 后续如果结合 TensorRT / profiling / 低精度路线，应该从哪条现有主线接，而不是从零散版本上重新试一遍。

所以这份文档的目标不是复读历史分数，而是把当前方法库整理成一个可执行的决策表。

## 1.1 当前起效范围

从现在开始，这份文档视为当前项目的**唯一主决策文档**，同时覆盖三类信息：

1. 线上已验证版本与方法判断；
2. Apple 本机轻量验证的能力边界与局部证据；
3. 后续可继续叠加的优化点、验证顺序与优先级。

原来的两份本地验证文档保留为归档材料，但后续若出现结论冲突，以本文件为准。

## 1.2 外部可借鉴技术的使用原则

最近补充查阅了一批外部项目与其背后的正式技术线。当前值得吸收的不是业务代码，而是以下三类方法论：

1. **ShuffleNetV2 / PaddleClas 路线：目标平台速度优先，不只看 FLOPs**
2. **Paddle-Lite 路线：导出模型 -> 优化 -> benchmark -> 部署 的完整闭环**
3. **PP-OCR 路线：轻量主干 + 多个小工程优化 + 任务特定后处理**

它们对当前 `infer.py` 的真正启发是：

- 先确认真实执行路径，再谈优化成立；
- 先做端到端时间拆解，再判断瓶颈在结构、调度还是 I/O；
- 不把单个技巧神化，而是用证据链验证一组小优化是否能稳定叠加。

## 2. 统一评估标准

后面所有版本判断都按这 5 个维度：

| 维度 | 判断标准 |
|---|---|
| 真实收益 | 是否显著降低 latency，且不是一次性偶然收益 |
| 合规性 | 是否改变结构规则、是否有已知违规风险 |
| 数值稳定性 | AUC / PCOC 是否稳定，是否依赖脆弱校正 |
| 工程延展性 | 是否容易继续叠加别的优化，而不是死路 |
| TensorRT 承接性 | 后续是否适合作为 ONNX / TensorRT / 低精度实验入口 |

最终把版本或方法分成 4 类：

- `主线保留`：已证明有效，后续继续叠加
- `待复测`：思路成立，但本地包/验证流程/平台异常还没给出可信结论
- `建议归档`：已有证据表明不值得继续投入
- `研究备份`：可保留为方向样本，但不进入当前主线

## 2.1 违规边界补充

仅靠“真实收益 / 合规性 / 数值稳定性”这类抽象维度还不够。结合你补充的规则截图，下面这些内容必须写死成当前方法库的**硬边界**，否则后面很容易把“更快”误判成“可晋级”。

### A. 输入采样 / 截断类，全部判违规

以下做法即使更快，也不能进入主线：

- 只跑部分 batch、sampling、subset；
- 设置 `max_batches`、`limit_batches`、跳过某些 batch；
- 在 submission 的 `infer.py` 里主动把 `max_ctx_len` 调小；
- 任何把正式输入规模改小、改稀、改短的行为。

因此：

- 本地轻量测试脚本可以抽样；
- 但 submission 版本里绝不能带入这些逻辑。

### B. 结构性删层 / 跳层 / 减少有效计算单元，全部判违规

以下都不应继续作为可晋级路线：

- Transformer 层数减少；
- ZeroLayer / SkipLayer / 直接在中间层 return；
- 删除完整 attention 主路径；
- 删除完整一层 SMoE；
- 把有效 expert 数变小；
- 把 `Top-K` 从 `K=2` 改成 `K<2`；
- 删除 `RepEncoder` 中的大模块层。

这也解释了为什么：

- `V120-V129` 这类跳层版本即使分高，也只能作为反例记录；
- 后续如果做剪枝，必须始终保持在“细粒度、数学可解释、可控近似”的范围内。

### C. 破坏输入语义 / forward 拓扑，全部判违规

以下行为不应进入主线：

- 为了提速改 `slot_mask`、输入 mask 语义；
- 为了提速改 `RepEncoder` 的输入语义；
- 静态跳过某些 embedding 表或 slot；
- 用默认零值 / 常量 / 伪 mask 替代真实输入处理。

所以后续无论是：

- `torch.compile`
- TensorRT / ONNX 改图
- Triton / kernel fusion
- layout 改写

都只能优化执行方式，不能改变输入经过网络的真实语义。

### D. 作弊型计时 / 预计算 / 查表，全部判违规

以下都要直接归入“淘汰”：

- monkey-patch `time` / `perf_counter` / `cuda.Event`；
- 把真正的 forward 挪出计时区；
- 正式 batch 之前用 dummy 逻辑提前算完；
- 离线生成 `logit_cache` / `pred_cache` / 查表字典；
- 靠后台线程、异步流、预写文件把结果偷运出计时区；
- 直接输出预先准备的 `predict.txt`。

这条对当前版本库的判断非常重要：

- 合法 warmup 可以保留；
- 合法 compile 首次触发可以保留；
- 但“把正式计算伪装成预热”必须直接判违规。

### E. 当前真正值得继续的合规优化层

根据截图里的允许项，后续主线只应集中在这些层面：

- 精度：`fp16/bf16/int8/fp8/W8A8/W4A16`
- 算子：FlashAttention、Triton/CUDA kernel、fused MLP / LayerNorm / gate
- 推理：`torch.compile`、CUDA Graph、多 stream
- 内存：预分配、pinned memory、零拷贝、cache 复用
- 调度：batch grouping、padding 优化、pack/varlen、动态 batch
- MoE：grouped GEMM、topk 优化、expert 并行（前提是有效 expert 数和 `K=2` 不变）
- I/O：异步加载、prefetch、batch 重排

因此，后面这份总表里所有“主线保留 / 待复测”的方法，都应默认限定在这类工程优化里，而不是重新回到删层、减 K、输入简化这类违规方向。

## 3. 当前方法库的总判断

先给结论，再展开。

### 3.1 应保留为主线的方法

1. `V139-FLASH-ATTN-sxyq` 这一条 attention 基线  
   这是当前所有后续优化的稳定底座，不是最终最优，但它定义了当前可用的 attention 加速基线。

2. `V109-DENSE-SMOE` 这一条“把不规则计算规整成 dense GEMM”的思路  
   这是当前最成功的 SMoE 工程化方向，后续不论是 SVD、剪枝还是 TensorRT，都应该建立在这类规整计算上，而不是回到 sparse dispatch。

3. `V153 -> V176` 这一条 FFN 结构化剪枝主线  
   这是目前最像“低风险继续拿收益”的方向。V153 已证明 25% FFN 剪枝在独立分支上几乎零代价，V176 则是它和 V169 混合方案的自然叠加。

4. `V168/V169/V171` 这一条 SVD / 混合方案主线  
   这是当前最强的合规主线。它的优势不只是分高，而是逻辑完整：减少真实 FLOPs、数值可控、可继续叠加。

### 3.2 应优先复测的方法

1. `V176-FFN-PRUNE-sxyq`  
   当前最值得复测。历史判断显示它更像被打包错误耽误，而不是方法本身失效。

2. `V175-HEAD-PRUNE-FIX-sxyq`  
   需要确认修复 reshape 后，head 剪枝在 `V169` 基线上的真实 latency 收益和 PCOC 漂移情况。

3. `V175-AUTOTUNE-sxyq` / `V179-PURE-ENGINEERING-sxyq` / `V180-MAXAUTOTUNE-sxyq`  
   这几条本质是在 `torch.compile` 模式上继续压榨工程收益。它们不是结构创新，但属于当前最便宜的系统级收益候选。

4. `V177-FFN-NOBIAS-sxyq` / `V178-FFN-SVD32-sxyq` / `V181-FFN-PRUNE50-sxyq`  
   这几条更像对 `V176` 的边界探测，价值在于拆分风险来源，不是直接做主线。

### 3.3 应明确归档的方法

1. 稀疏路由 / sparse dispatch 一整条分支  
   包括 `V146`、`V150`、`V151`、`V152`，以及本地现存的 `V157-TRITON-MOE`、`V157A`、`V157C`、`V159`、`V160`、`V163`、`V164`。  
   当前证据很一致：在这套推理链路里，稀疏调度开销大于算力节省。

2. eager mode 下的 INT8 路线  
   包括 `V105`、`V147`、`V162`、`V165`。  
   当前结论也很一致：反量化和访存组织的副作用大于收益。

3. 没有 shape 治理的 compile / CUDA Graph 试法  
   包括 `V142`、`V149`、`V166`。  
   问题不是 compile 本身，而是 shape 抖动和 warmup 缺失。

4. 改变计算逻辑导致 PCOC 崩坏的路线  
   包括 `V136-FUSED-OPT`、`V157-HEAD-PRUNE` 原版。  
   这些可以当反例保留，但不应继续当主线。

## 4. 分方法线详细评估

### 4.1 Embedding 路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V16-FP16EMB-sxyq` | `研究备份` | 早期证明了 dtype 调整有一定价值，但收益有限，且已被后续更强主线覆盖 | 不单独继续 |
| `V24-SPARSE-EMB-sxyq` | `保留经验` | `embedding_bag` 说明 embedding 后处理融合方向是对的 | 作为 embedding 融合思路保留 |
| `V139` 及其后续继承线 | `主线保留` | embedding 已融入后续混合版本，不再是独立战场 | 后续更多转向访存和融合 |

判断：

- embedding 是瓶颈，但不是当前最直接的得分入口。
- 它更适合在后续 TensorRT / Triton / 自定义 kernel 路线中处理。
- 当前阶段不建议回到“单独抠 embedding 小优化”。

### 4.2 Attention 路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V103-PER-USER-CAUSAL-SDPA-sxyq` | `历史基线` | 证明 per-user causal SDPA 比更早基线强，但已被后续版本超越 | 仅作对照 |
| `V139-FLASH-ATTN-sxyq` | `主线保留` | 当前 attention 加速基线稳定、收益真实 | 作为后续所有实验对照底座 |
| `V143-PERMUTE-OPT-sxyq` | `建议归档` | 说明 eager 细碎张量整理几乎已到收益上限 | 不继续投入 |
| `V175-HEAD-PRUNE-FIX-sxyq` | `待复测` | head 剪枝理论上能打 attention 主瓶颈，但 PCOC 风险高 | 仅做单变量复测 |

判断：

- attention 仍是当前真正的主瓶颈之一。
- 但在 PyTorch eager 范式下，继续做 `permute`、参数预计算之类的小修基本没有性价比。
- 后续更值得做的是：
  1. head 剪枝的可控复测；
  2. packed/jagged layout 的 feasibility；
  3. ONNX / TensorRT 下 attention kernel 承接性验证。

### 4.3 Dense SMoE 与 Sparse MoE 路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V109-DENSE-SMOE-sxyq` | `主线保留` | 当前最成功的 MoE 工程化形态，规整成 batched GEMM 后真实提速 | 继续作为底座 |
| `V146-SPARSE-OPT-sxyq` | `建议归档` | dispatch 开销远超节省的计算 | 不继续 |
| `V150/151/152` | `建议归档` | Grouped BMM、no-sync、prealloc 都没打中根因 | 不继续 |
| `V157-TRITON-MOE-sxyq` | `研究备份` | 思路有探索价值，但当前缺少可信线上验证 | 不进主线 |
| `V157A/SPARSE-ONLY`、`V157C/SPARSE-NOPRUNE`、`V159`、`V160`、`V163`、`V164` | `建议归档` | 从命名和实现看仍围绕 sparse 路由或关闭 dense 方案，方向已被历史证据否定 | 不继续 |
| `V161-TOP1-GATE-sxyq` | `研究备份` | top1 gate 有可能减少计算，但存在明显分布漂移风险 | 除非单独验证，否则不推进 |

判断：

- 这条线已经有足够多反例，不需要再反复证明 sparse dispatch 在当前链路里很难赢。
- 后续如果还做 MoE 优化，只做两类事：
  1. 继续把计算规整成 dense / batched 形态；
  2. 交给更强的编译器或 kernel 系统（TensorRT / Triton / plugin）处理。

### 4.4 Compile / Warmup / Autotune 路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V142-COMPILE-SMOE-sxyq` | `建议归档` | 动态 shape 重编译，属于反面教材 | 不继续 |
| `V149-CUDA-GRAPH-sxyq` | `建议归档` | 固定 padding 带来的浪费大于 graph 收益 | 不继续 |
| `V166-CUDA-GRAPH-sxyq` | `建议归档` | 没有 warmup 机制，编译收益被初始化开销吃掉 | 不继续 |
| `V169-HYBRID-SVD-sxyq` | `主线保留` | 证明 compile 只有在 warmup 和混合优化配合下才有意义 | 作为正确用法保留 |
| `V175-AUTOTUNE-sxyq` | `待复测` | `max-autotune-no-cudagraphs` 是比较合理的工程方向 | 可做单变量验证 |
| `V178-MAXAUTOTUNE-sxyq` | `待复测` | compile mode 切到 `default`，更像对照试验 | 用来拆分 compile mode 收益 |
| `V179-PURE-ENGINEERING-sxyq` | `待复测` | 从代码看尝试把 `rep_encoder` 也纳入 compile，是低风险系统优化 | 值得单独验证 |
| `V180-MAXAUTOTUNE-sxyq` | `待复测` | compile mode 切到 `max-autotune`，属于工程挖潜 | 值得和 V175/V179 对照 |

判断：

- compile 这条线没有死，死的是“没做 shape 治理的 compile”。
- 当前最值得做的不是再发明一个 compile 版本，而是把它拆成严格单变量实验：
  1. compile mode 变化；
  2. compile 模块范围变化；
  3. 是否 warmup；
  4. shape bucket 是否收敛。

### 4.5 量化路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V105-ALL-IN-INT8` | `建议归档` | 全量 eager INT8 不成立 | 不继续 |
| `V147-INT8-QUANT-sxyq` | `建议归档` | dequant 开销抵消收益 | 不继续 |
| `V162-INT8-SMOE-sxyq` | `建议归档` | Dense SMoE + INT8 在当前实现下仍不划算 | 不继续 |
| `V165-INT8-DENSE-sxyq` | `建议归档` | 2x 变慢，已经给出明确反证 | 不继续 |

判断：

- 当前仓库不应该继续做 eager mode 的 INT8 试错。
- 量化后续只保留一条路：
  - 先在 `V169/V176` 上做 FP16/BF16 稳定基线；
  - 然后在 ONNX / TensorRT / ModelOpt 路线上做 PTQ；
  - PTQ 不够再判断是否需要混合精度或 QAT。

### 4.6 剪枝路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V153-PRUNE-FFN-sxyq` | `主线保留` | 已验证零开销减算量有效，且 AUC 稳 | 继续承接 |
| `V154-PRUNE50-sxyq` | `研究备份` | 50% 剪枝没有继续变快，说明激进剪枝并不线性收益 | 不做主线 |
| `V167-AGGRESSIVE-PRUNE-sxyq` | `研究备份` | 进一步激进剪枝风险更高 | 仅作边界参考 |
| `V173-HEAD-PRUNE-sxyq` / `V174-DUAL-PRUNE-sxyq` | `建议归档` | 当前版本已知有实现 bug，不具备直接参考意义 | 只保留教训 |
| `V175-HEAD-PRUNE-FIX-sxyq` | `待复测` | bug 已知修复，但数值风险仍在 | 单独复测 |
| `V181-FFN-PRUNE50-sxyq` | `研究备份` | 50% FFN 剪枝 + SVD 适合作为上界探测，不适合作为默认主线 | 不优先 |

判断：

- 结构化剪枝是当前唯一已经被多次证明有效的“合规减算量”路径。
- 但这条线也必须分开看：
  - `FFN 剪枝`：可继续推进；
  - `head 剪枝`：要谨慎，收益可能有，但 PCOC 风险大；
  - `激进剪枝`：只做边界实验。

### 4.7 SVD / 结构压缩路线

| 代表版本 | 当前判断 | 原因 | 后续动作 |
|---|---|---|---|
| `V168-SVD-LOWRANK-sxyq` | `主线保留` | 是 SVD 独立贡献的关键基线 | 必须保留 |
| `V169-HYBRID-SVD-sxyq` | `主线保留` | 当前最佳合规版本，且组合逻辑最完整 | 当前主线中心 |

- 这条线是当前主线中的主线。

## 5.1 已并入的本地轻量验证结论

下面这些内容原本分散在两份本地验证文档里，现在统一并入这里，作为后续所有“本地证据”的固定解释口径。

### Apple 本机环境能做什么

- 可以做 `seq_encoder` / attention 主干的 MPS 可行性验证；
- 可以做 `RepEncoder@CPU -> seq/head@MPS` 的 split-device 验证；
- 可以做真实格式小样本、holdout、小规模 batch 组织与结构代理测试；
- 不能把 Apple MPS 结果直接等同于 AI Studio CUDA 最终 latency。

### Apple 本机环境不能替代什么

- 不能替代云端正式环境下的真实 leaderboard 结论；
- 不能替代 CUDA kernel、TensorRT、Nsight 的最终判断；
- 不能把本地 synthetic / split-device 的排名直接当成线上最终胜负。

### 本地验证已经给出的稳定结论

1. `V182-FFN25-SVD64FP32-sxyq` 一度是本地结构代理上的强候选，说明 `prune25 + rank64 + FP32-SVD` 这条结构线在 CPU / split-device 代理上是成立的。
2. `V185` 赢在**结构收益 + 校准修复 + CUDA runtime 叠加**，并不等价于“本地主干结构一定最强”。
3. `V186` 这类异步 prefetch 版本在线上没有自动兑现收益，说明文档允许的 I/O 优化仍需按真实环境逐项验证。
4. `V187` 的 balanced batching 只有在拿回 `DataLoader` 路径控制权后才有意义；因此 `V188` 比 `V187` 更能代表这条线的真实价值。

### 当前本地证据如何使用

- 若目标是继续冲线上总分：以 `V194` 为主线；
- 若目标是继续研究结构代理和局部上界：保留 `V182` 作为历史结构证据；
- 若目标是验证调度层优化是否真实进入线上路径：从 `V188` 往后推，而不是回看 `V187` 的原始分数。
- 若目标是继续研究 TRT 线上的“哪些变量还能加”：以 `V194` 为起点做单变量实验，不再默认从 `V195` 继续叠更多高风险项。

## 6. 结合当前优化方案后的明确行动顺序

### 6.1 第一层：先把主线整理干净

后续不要再把所有版本一股脑都当候选。应先固定 4 个角色：

| 角色 | 版本 |
|---|---|
| attention 基线 | `V139-FLASH-ATTN-sxyq` |
| 当前线上主线 | `V207-EMB-INT8-ONLY-sxyq` |
| 结构压缩参考主线 | `V185-V177-STACKED-SUBMIT-sxyq` |
| TRT 单变量继续叠加候选 | `V207 + timing cache/profile` / `V207 + runtime overlap` / `V205 + selective PTQ` |
| MoE 过渡样本 | `V193-MOE-DISPATCH-sxyq` |
| 诊断候选 | `V191-PROFILE-TIMING-sxyq` / `V195-TRT-MOE-HIGHRISK-sxyq` / `V204-SELECTIVE-QUANT-sxyq` |
| 工程反证样本 | `V186-ASYNC-PREFETCH-sxyq` / `V190-SHAPE-STABLE-sxyq` / `V208-MAX-STACKED-HIGHRISK-sxyq` |

这样后续每轮实验只围绕这 4 个角色推进，其他版本只在需要诊断时回头。

### 6.2 第二层：立即应该做的复测顺序

按优先级排序：

1. `V207 + TRT build/runtime timing cache/profile`  
   原因：`V207` 已经是当前最高分，下一步最应该做的是压榨这条已经被线上验证过的 `embedding INT8 + TRT plugin` 主链路，而不是回退到更早的底座。

2. `V205 + selective INT8 PTQ（非 MoE 子图）`  
   原因：量化如果继续做，不应回到 eager INT8，也不该停留在 `V204` 这种过渡态；应直接以 `V205` 这个文档严格对齐的 PTQ-prep 版本为编号起点，先保持 `MoE plugin=FP16` 不动。

3. `V207` 上继续拆单变量：`Fused Top2 / rep count-matmul / rep norm-linear fuse / pin_memory + non_blocking`  
   原因：`V202` 已证明“整组吞吐默认项一起叠”虽然有效，但整包默认打开并不占优；现在更合理的是在 `V207` 这个新主线上继续做可控叠加。

4. `V176-FFN-PRUNE-sxyq`  
   原因：保留为结构压缩参考线的最高优先级，不是因为它比 `V194` 更强，而是它仍是最干净的“真实减算量”路线。

5. `V177` / `V178-FFN-SVD32` / `V172` / `V175-HEAD-PRUNE-FIX-sxyq`  
   原因：继续保留为结构诊断，不是当前首要冲分版本。

### 6.3 第三层：和 TensorRT 路线如何接

如果结合前面整理出的 TensorRT 思路，当前项目现在应明确分成两条代表线：

1. `V139`  
   作用：attention 主基线，适合做 ONNX / TensorRT attention 承接性验证。

2. `V207`  
   作用：当前 TRT-MoE plugin 总主线，适合做 timing cache、profile、runtime overlap，以及围绕 embedding INT8 的继续叠加。

3. `V185` 或 `V176`  
   作用：结构压缩参考主线，适合保留“真实减算量”的对照地位，并承担和 TRT 路线做横向验证的角色。

原因：

- `V139` 代表“attention 主瓶颈”的原始强基线；
- `V207` 代表“plugin/kernel 原生组合 + embedding INT8 单变量” 当前已经拿到真实线上优势的主线；
- `V185/V176` 代表“真实减算量”的结构压缩参考方案；
- 稀疏路由、eager INT8、无 shape 治理 compile 都不值得作为 TensorRT 起点。

### 6.4 外部技术借鉴与可验证优化点

最近额外核查了几类外部项目及其背后的正式技术线。结论是：不要照搬业务仓库代码，而要吸收它们已经被论文或官方工具链验证过的方法论。当前真正值得写入主线研究的只有下表这些点。

| 来源线 | 可借鉴点 | 对当前 `infer.py` 的映射 | 是否已部分实现 | 下一步验证方式 |
|---|---|---|---|---|
| ShuffleNetV2 / PaddleClas | **目标平台速度优先于 FLOPs** | 不先相信理论减算量，先确认真实执行路径、真实 latency、真实 shape 行为 | 已部分实现：`V185`~`V189` 已开始围绕真实路径和 batch 形状做验证 | 固化“源码路径 -> batch 路径 -> latency”证据链；新增每版是否命中 `cached_batches` 的显式记录 |
| Paddle-Lite 部署闭环 | **导出 -> 优化 -> benchmark -> 部署** | 把当前 `infer.py` 优化拆成 build/prepare/runtime 三段，不再只盯 forward | 尚未完整实现 | 新增 `ONNX / TensorRT / runtime` 三段验证清单，先从 `V139`、`V169/V176` 两条线做最小闭环 |
| PP-OCR 工程路线 | **轻量主干 + 多个 bag of tricks 叠加** | 不追单个神奇 trick，而是允许 batch 组织、I/O、warmup、校准、构图方式小步叠加 | 已部分实现：`bias`、`prefetch`、`balanced batching`、`forced dataloader` | 每次只加一个变量；同时记录“是否真的进入执行路径” |
| PaddleOCR / QPT 类桌面工具经验 | **任务后处理和主干推理分开分析** | 区分结构收益、校准收益、I/O 收益、数据准备收益 | 已部分实现：`bias` 被单独识别为校准项 | 后续所有报告必须把 `score` 拆成结构、校准、调度三层解释，不能混写 |

### 当前最值得继续验证的“外部借鉴 -> 本地实现”映射

1. **执行路径控制权验证**  
   这是从“目标平台速度优先”直接映射出来的第一原则。  
   具体要继续检查：
   - 是否命中 `cached_batches`
   - `Dataset / make_collate_fn` 是否真的生效
   - `balanced batching` 是否真实进入线上路径

2. **端到端分段计时验证**  
   这是从 Paddle-Lite 的部署闭环映射来的。  
   后续每版至少拆成：
   - 数据读取 / batch 构造
   - H2D / prepare
   - 主干 forward
   - 输出收集 / 写回

3. **小优化叠加的单变量验证**  
   这是从 PP-OCR 的 bag-of-tricks 路线映射来的。  
   当前最适合继续逐项验证的点只有：
   - `shape bucket / batch 顺序治理`
   - `async prefetch / runtime overlap`
   - `compile module 范围`
   - `warmup 起始 batch 选择`

4. **结构收益与校准收益分离验证**  
   这是当前最容易被误判的一块。  
   必须继续区分：
   - `SVD / prune` 带来的真实结构收益
   - `bias bake-in` 带来的校准收益
   - `balanced batching / prefetch` 带来的调度收益

只有这种分层验证方式，才能避免把“一个分数更高的 stacked 包”误写成“每一层方法都有效”。

## 7. 更详细的后续优化策略

### P0：先做实验治理，不再继续失控扩散版本

每轮必须固定记录：

1. 改动点只有一个；
2. latency；
3. AUC / PCOC；
4. 显存；
5. 是否需要 warmup；
6. 是否存在平台打包风险；
7. 是否可复现。

如果这些字段缺一个，就不应把结果吸收到主线。

### P1：短期冲分只做两类优化

1. `零开销减算量`
   - FFN 剪枝
   - SVD
   - 可控的 head 剪枝

2. `低风险工程收益`
   - compile mode
   - compile 范围
   - warmup
   - shape bucket

理由很简单：这两类是当前历史上唯一有持续正反馈的方向。

### P2：中期再接 TensorRT / ONNX / PTQ

顺序必须固定：

1. 先用 `V139`、`V169/V176` 建 ONNX 导出和数值回归链；
2. 再做 FP16 TensorRT engine；
3. 再做 shape profile / bucket；
4. 再评估 PTQ；
5. PTQ 不够再做敏感层保护或混合精度；
6. 最后才讨论 plugin。

### P3：明确不再优先的方向

1. sparse dispatch 系列
2. eager mode INT8 系列
3. 无 shape 治理的 CUDA Graph / compile
4. 激进剪枝
5. 改 gate 逻辑的方案

这些方向不是“理论永远不可能”，而是对于当前这条 submission 主线，证据已经足够表明它们不是高 ROI 路线。

## 8. 最终结论

如果把当前方法库压成一句话，结论就是：

**主线已经更新为“双轨制”：线上冲分主线切到 `V194` 的 TRT-MoE plugin 路线；`V185 -> V176` 保留为结构压缩参考线。后续不再默认把高风险变量继续堆到 `V195` 上，而是围绕 `V194` 做单变量 TRT/runtime/量化实验，并用 `V185/V176` 做结构对照。**

更具体一点：

1. `V169` 是当前最稳的中心版本；
2. `V176` 是当前最值得优先复测的冲分版本；
3. `V179/V180` 是当前最便宜的系统收益候选；
4. `V175-HEAD-PRUNE-FIX` 可以做，但优先级低于 `V176`；
5. 稀疏路由、eager INT8、失控 compile 这三条线应停止继续扩张。
